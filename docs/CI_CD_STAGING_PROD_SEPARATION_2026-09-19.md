## Problem

```
push to main → e2e-tests.yml (3 Jobs sequenziell)
  Job 1: Build + DEV E2E        ~10-15 Min
  Job 2: Deploy Staging + E2E   ~15-20 Min
  Job 3: Deploy Production       ~5-10 Min
  ─────────────────────────────────────────
  TOTAL:                         ~30-45 Min

Problem: Staging erst nach 25-30 Min verfügbar
         (Image muss erst durch DEV E2E durchlaufen)
```

## Lösung

```
Zwei parallele Workflows bei push to main:

  staging.yml (NEU)                    e2e-tests.yml (BLEIBT)
  ─────────────────                    ──────────────────────
  Build Image                          Build Image
  Push to Docker Hub                   DEV E2E Tests
  Deploy Staging                       Deploy Staging
  Health Check                         Staging E2E Tests
                                       Deploy Production
  Dauer: ~10-15 Min ⚡                 Dauer: ~30-45 Min 🔒
```

### Ergebnis

```
push to main (z.B. fix: sentinel semaphore):
  │
  ├─→ staging.yml (STARTET SOFORT)
  │     Build → Push → Deploy Staging → Health Check
  │     → Staging in ~10 Min testbar ⚡
  │
  └─→ e2e-tests.yml (STARTET SOFORT)
        Build → DEV E2E → Staging E2E → Deploy Prod
        → Production in ~30-45 Min (geschützt) 🔒
```

## Was staging.yml macht

```
1. Build Backend Image (amd64 + arm64)
2. Push to Docker Hub
3. Build Frontend (amd64 + arm64)
4. Push to Docker Hub
5. Configure K8s Context (Staging)
6. Ensure Docker Hub Pull Secret
7. Deploy Backend
8. Deploy Frontend
9. Deploy Celery Workers
10. Health Check
```

## Was staging.yml NICHT macht

```
❌ DEV E2E Tests (das macht e2e-tests.yml)
❌ Staging E2E Tests (das macht e2e-tests.yml)
❌ Production Deploy (das macht e2e-tests.yml)
❌ KEDA Secrets Update (das macht e2e-tests.yml)
❌ System CronJobs (das macht e2e-tests.yml)
```

## Warum das sicher ist

```
1. Gleicher ImageTag (commit SHA)
   → staging.yml und e2e-tests.yml bauen dasselbe Image

2. Keine Daten-Konflikte
   → Staging hat eigene DB, eigene Secrets

3. Production bleibt geschützt
   → e2e-tests.yml hat E2E Gates (≥95% Pass Rate)

4. Rollback möglich
   → Bei Problemen: kubectl rollout undo auf Staging
```

## Concurrency Groups

```
staging.yml:
  group: staging-${{ github.ref }}
  → Nur ein Staging-Deploy gleichzeitig

e2e-tests.yml:
  group: ${{ github.workflow }}-${{ github.ref }}
  → Nur ein Full-Pipeline gleichzeitig

Beide laufen PARALLEL (unterschiedliche Groups)
```

## Trigger

```
staging.yml:   push to main (NUR main)
e2e-tests.yml: push to main + pull_request to main

→ Bei PR: Nur e2e-tests.yml (DEV E2E)
→ Bei Push to main: BEIDE parallel
```

## Risiken

```
Risiko 1: Doppeltes Image-Build
  → Beide Workflows bauen das Image
  → Löst sich auf (Docker Layer Caching)
  → Akzeptabel für Staging-Speed

Risiko 2: Race Condition beim Deploy
  → Beide versuchen Staging zu deployen
  → Concurrency Groups verhindern das
  → staging.yml deployed SOFORT, e2e-tests.yml deployed NACH E2E

Risiko 3: Docker Hub Rate Limit
  → 2x Push pro Commit
  → Paid Account hat 200 pulls/6h
  → Kein Problem bei normaler Nutzung
```
