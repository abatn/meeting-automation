## 1. Information Security Management System (ISMS)

Das System adoptiert einen risikobasierten Ansatz zur Informationssicherheit gemäß ISO 27001:2022 Annex A Controls.

## 2. Implementierte Security Controls (Kategorie 1)

### 2.1 Authentifizierung und Anwendungssicherheit (A.5.17 / A.8.26)
- **JWT-Auth & RBAC**: Vollständige JWT-basierte Authentifizierung in FastAPI (6 Rollen: DG, Manager, Participant, System Admin, Tech Admin, Admin)
- **Session-Blacklisting**: Redis-basierte Token-Blacklist für sicheren Logout (verhindert Replay-Angriffe)
- **Input-Validierung**: Strikte Input-Validierung für jeden API-Call durch FastAPI und Pydantic
- **Monitoring Access Control**: `/metrics` Endpoint nur intern erreichbar (PodIP, kein Ingress-Exposure) — Auth entfernt da Prometheus Scraping erfordert unauthentifizierten Zugriff (Phase 110). Prometheus selbst geschützt via Basic Auth am Ingress (A.9 konform)
- **Audit-Logging**: Monitoring-Endpoints protokolliert Zugriffe in `audit_logs` (ISO 27001 A.12.4)

### 2.2 Datensicherheit & Kryptographie (A.8.24 / A.10)
- **Verschlüsselung at Rest**: SQLAlchemy `EncryptedType` (Fernet AES-128) verschlüsselt sensible Inhalte (PV-Daten, MFA-Secrets) auf Datenbankebene
- **Passwort-Hashing**: Sicheres Hashing via bcrypt
- **ENCRYPTION_KEY**: In K8s ConfigMap hinterlegt (korrekter Fernet-Key, verifiziert Phase 30)

### 2.3 Audit & Logging (ISO 27035 / A.12.4.1)
- **AuditMiddleware**: Speichert alle sicherheitsrelevanten Anfragen (POST/PUT/DELETE) inklusive Benutzer-ID, IP und Aktion in dedizierter `audit_logs` Tabelle
- **Session-Isolierung**: Audit-Logging verwendet dedizierte `AsyncSessionLocal()` Session — unabhängig von FastAPI's Request-Lifecycle
- **Fehlerbehandlung**: `db.rollback()` im except-Block verhindert "Session als FAILED markiert"
- **Sicheres Logging**: Anonyme oder veraltete Sessions werden als Metadaten (`stale_user_id`) erfasst

### 2.4 Informationsweitergabe (A.5.14)
- **n8n Webhook Security**: Backend verlangt von n8n den Header `X-Internal-API-Key` für Datenabrufe
- **n8n UI**: NodePort 31678, NetworkPolicy erlaubt nur Ingress auf Port 5678

### 2.5 Celery Tenant Isolation (A.5.15 / A.8.26)
- **Problem**: `_process_recording_pipeline()` queryte `Recording` nur nach `Recording.id`, ohne `client_id` Filter
- **Fix**: `client_id` Parameter zur Pipeline-Funktion hinzugefügt. Alle Queries filtern nach `Recording.id AND Recording.client_id`
- **Tests**: 3 Security-Tests bestehen (vorher `xfail`)
- **Pipeline-Metriken**: `client_id` Label in allen Business-Metriken (Recordings, Transcriptions, PV Sections, Actions)
- **Storage-Monitoring**: Periodische Quota-Prüfung (alle 15 Min) mit Threshold-Alerts (50%, 70%, 90%)

Oracle Cloud Infrastructure Security List — externe Ports:

| Port | Protokoll | Zweck | Status |
|------|-----------|-------|--------|
| 80 | TCP | nginx-ingress HTTP (hostPort) | ✅ Geöffnet (Phase 55) |
| 443 | TCP | nginx-ingress HTTPS (hostPort) | ✅ Geöffnet (Phase 55) |
| 31362 | TCP | Frontend NodePort (Legacy) | ✅ Geöffnet |
| 31678 | TCP | n8n UI NodePort | ✅ Geöffnet |
| 32222 | TCP | Backend NodePort (Legacy) | ✅ Geöffnet |
| 7880 | TCP | LiveKit Signaling (via nginx-ingress) | ✅ Geöffnet |
| 7881 | TCP | LiveKit ICE TCP (via nginx-ingress) | ✅ Geöffnet |
| 3478 | UDP | LiveKit TURN | ✅ Geöffnet |
| 8472 | **UDP (Protocol 17)** | Flannel VXLAN (Cross-node Pod-Netzwerk) | ✅ Geöffnet |

**Hinweis**: Ports 80/443 werden für `staging.meeting-automation.com` via Let's Encrypt HTTP-01 Challenge und LiveKit WebSocket benötigt. LiveKit WebSocket-Endpunkte: `/rtc` + `/twirp` via nginx-ingress (Phase 56). LiveKit nutzt `force_tcp: true` (Phase 122) — WebRTC Media über TCP statt UDP, daher keine UDP 50000-60000 Port-Weiterleitung nötig.

**Hinweis hostNetwork (Phase 96/122)**: ingress-nginx läuft mit `hostNetwork: true` auf Node 1 (gleicher Node wie Backend-Pods). LiveKit wurde in Phase 122 von hostNetwork auf normalen Pod umgestellt (Pod-IP via flannel VXLAN). Cross-Node hostNetwork-Traffic wird von NetworkPolicies NICHT korrekt behandelt — `namespaceSelector`, `podSelector` und `ipBlock` funktionieren nicht zuverlässig für hostNetwork-Pods über Nodes hinweg (CNI kann Quell-Pod nicht identifizieren). Alle hostNetwork-Pods müssen auf demselben Node laufen wie ihre Ziel-Services.

### 3.3 firewalld Konfiguration (ISO 27001 A.8.20 / A.8.22)

firewalld bleibt auf allen Nodes aktiv (Defense-in-Depth). K3s-spezifische Konfiguration:

| Zone | Source | Zweck |
|------|--------|-------|
| trusted | 10.42.0.0/16 | Pod-CIDR — alle Pod-zu-Pod-Verbindungen erlaubt |
| trusted | 10.43.0.0/16 | Service-CIDR — alle Service-zu-Pod-Verbindungen erlaubt |
| trusted | 10.0.0.0/24 | Host-CIDR — Node-zu-Node für Monitoring (Node 2, Phase 110) |

| Port | Protokoll | Zweck |
|------|-----------|-------|
| 6443 | TCP | Kubernetes API Server |
| 10250 | TCP | Kubelet Metrics/API |
| 8472 | UDP | Flannel VXLAN |
| 5001 | TCP | Spegel (Container Registry Mirror) |
| 9100 | TCP | node-exporter Metrics (Node 2, Phase 110) |

**Begründung**: firewalld filtriert externen Traffic (OCI Security Lists sind erste Verteidigungslinie). Pod- und Service-IPs (10.42.x.x, 10.43.x.x) sind private Cluster-IPs, die nur intern erreichbar sind — `trusted` Zone ist sicher und nötig für k3s.
