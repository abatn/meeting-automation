### Phase 122: LiveKit hostNetwork entfernt — Cross-Node Fix (2026-07-02)
- **Status**: ✅ ABGESCHLOSSEN

#### Root Cause (verifiziert mit Beweis)
**LiveKit hatte `hostNetwork: true` auf Node 1, Redis läuft auf Node 2.**
- HostNetwork-Pods nutzen Host-Routing (NICHT flannel VXLAN)
- OCI Security List blockiert Host-to-Host TCP zwischen Node 1 und Node 2
- Nur UDP 8472 (flannel VXLAN) funktioniert cross-node
- NetworkPolicy kann hostNetwork-Pods nicht matchen (Quelle = Node-IP, nicht Pod-IP)
- `default-deny-all` + fehlende Ingress-Regeln in `livekit-policy` → alles blockiert

**Beweis:**
| Test | Ergebnis |
|------|----------|
| HostNetwork-Pod → Redis ClusterIP | Connection refused |
| HostNetwork-Pod → Redis Pod IP | Connection refused |
| HostNetwork-Pod → Ping Node 2 | 100% packet loss |
| Backend-Pod → Redis ClusterIP | OK (flannel VXLAN) |
| nginx-ingress → LiveKit (gleicher Node) | OK (hostNetwork Bypass) |

**Erkenntnisse (aus .loop.md Phase 95/96):**
- hostNetwork-Pods: `namespaceSelector`/`podSelector` funktionieren NICHT cross-node
- Gleicher-Node hostNetwork-Traffic umgeht NP-Eforcement
- hostNetwork entfernen = Pod-IP via flannel VXLAN = funktioniert

#### Was gemacht
| # | Aktion | Ergebnis |
|---|--------|----------|
| 1 | ConfigMap: `force_tcp: false` → `true` | WebRTC über TCP statt UDP (kein NodePort für 50000-60000 nötig) |
| 2 | livekit-policy: Ingress für `livekit-egress-staging` (7880/7881) + `policyTypes` | Egress → LiveKit Recording funktioniert |

| 5 | ISO27001.md: Policy-Tabelle korrigiert, Version 2.7 | Dokumentation stimmt mit Cluster überein |
| 6 | `kubectl replace` statt `kubectl apply` | hostNetwork kann nur via replace entfernt werden |

## ⚠️ CELERY OOM — Analyse + Empfehlungen (Phase 76, 2026-06-25)

> Recording `Test 13` (532 Utterances, ~54s Audio) verursachte 6x OOMKilled trotz 16Gi Memory Limit.
> **Bestehende Logik/Struktur bleibt unverändert** — nur Vermerk für zukünftige Optimierung.

### Root Cause
| Komponente | Speicher | Persistent? | Datei |
|------------|----------|-------------|-------|
| Sentinel LLM (Qwen-1.5B Q4_K_M) | **~1.5 GB** | ✅ Immer geladen (beim Import) | `sentinel_service.py:31,76` |
| ONNX ECAPA-TDNN (192-dim) | ~120 MB | ✅ Immer geladen | `speaker_embedding_service.py:63` |
| Python + Celery + SQLAlchemy | ~300 MB | ✅ | — |
| Speaker Batch (3× librosa+fbank+ONNX) | ~150 MB | ❌ Transient | `transcription_tasks.py:655` |
| Gladia Result Dict (532 utterances) | ~20 MB | ❌ Transient | `gladia_service.py:102` |

**Berechnung**: Default Concurrency = 4 Worker进程. Jeder lädt eigenes Sentinel (1.5 GB) + ONNX (120 MB) + Python (300 MB) = **4 × 1.92 GB = 7.68 GB NUR FÜR BASELINE**. Das übersteigt jedes Memory-Limit.

### Microsoft Teams Vergleich
- Teams Audio Processing: **1-2 GB pro Worker** (Cloud-basiert, kein lokales LLM)
- Teams Speaker Diarization: **ONNX/TensorRT, ~512 MB pro Session**
- **Key Difference**: Teams lädt KEIN 1.5GB LLM pro Worker — alles API-basiert (Azure OpenAI)

### Finaler Plan (geplant)
**Ziel**: 4 Workers behalten (für Production-Throughput), Memory pro Worker reduzieren.

| Fix | Datei | Effekt |
|-----|-------|--------|
| **1. Sentinel Lazy Loading** | `sentinel_service.py:76` | Erst laden wenn `summarize_chunk()` aufgerufen wird → Idle-Worker: 300 MB statt 1.5 GB |
| **2. --max-tasks-per-child=5** | K8s Deployment Command | Prozess-Recycling nach 5 Tasks → Memory Leaks werden bereinigt |
| **3. Container Memory** | K8s Deployment | **4 Gi** (Staging) / **8 Gi** (Production pro Tenant) |

### Memory-Verbrauch nach Fix
```
Idle:   4 × 300 MB = 1.2 GB (vorher: 4 × 1.92 GB = 7.68 GB)
Active: 2 × 1.92 GB + 2 × 300 MB = 4.44 GB (nicht alle 4 laden Sentinel gleichzeitig)
Peak:   ~5 GB → passt in 4 Gi Staging / 8 Gi Production
```

### Production Architektur (pro Tenant)
- Jeder Tenant hat eigene 4 Workers (Isolated Infrastructure)
- pro Tenant: 4 Gi RAM Minimum (Staging) / 8 Gi RAM (Production, ~25€/Monat Hetzner)
- Workers bleiben 4 — für Throughput nötig wenn mehrere Meetings gleichzeitig reinkommen

### Aktueller Workaround
- Recording `45cf941f` auf `failed` gesetzt (Pipeline abgebrochen)
- Bei normalen Meetings (kurze Aufzeichnung) funktioniert die Pipeline mit 2Gi + concurrency=4
- **Nur bei großen Recordings (>500 Utterances)** ist OOM verifiziert — genaue Grenze unbekannt
