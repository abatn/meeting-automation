### Phase 158: Navbar Avatar Overflow Fix — Mobile LTR (2026-07-09)
- **Status**: ✅ ABGESCHLOSSEN + DEPLOYED

#### Problem
Auf Viewports ≤360px (Smartphone) war der Profil-Avatar in LTR (EN/FR) außerhalb des Viewports. In RTL (Arabic) funktionierte es weil der Arabic-Text schmaler ist.

#### Root Cause (bewiesen via Playwright-Messung)
Branding-Text ("MeetingAutomation" in Inter = 149px) + fehlender `flexShrink: 0` auf Right Box → bei Viewports ≤360px Gesamtinhaltsbreite (354px) überstieg Viewport (360px-32px Padding = 328px).

**Messwerte LTR VORHER (320px):**
- Left Stack: 233px, Right Box: 121px, Gesamt: 354px
- Avatar rechts: 365px → außerhalb des Viewports ❌

**Messwerte RTL VORHER (320px):**
- Arabic-Text ~38px schmaler → Gesamt: ~316px → passt ✅

**Messwerte LTR NACHHER (320px):**
- Left Stack: 167px (schrumpft), Right Box: 121px (bleibt), Gesamt: 288px
- Avatar rechts: 299px → innerhalb des Viewports ✅

#### Andere Hypothesen — widerlegt durch Messung
- MUI-Cache: widerlegt (scrollWidth === clientWidth)
- Auth-State: widerlegt (Avatar im DOM, visible: true)
- CSS-Overflow: widerlegt (overflow: visible auf Toolbar/AppBar)
- position:fixed: widerlegt (width: 100%, left: 0)

#### WURZELURSACHEN (RC1–RC7, priorisiert)

##### RC1 (PRIMÄR): Handgeschriebene fbank-Extraktion weicht vom SpeechBrain-Training ab
Datei: `speaker_embedding_service.py:108-155` — drei belegte Abweichungen von hyperparams.yaml:
1. **FFT-Größe falsch**: Zeile 145 `np.fft.rfft(frame, n=2*(frame_length//2+1))` = n_fft **402** statt 400; Ergebnis (202 Bins) wird auf 201 abgeschnitten → verschobene Frequenz-Bin-Zuordnung zur 80×201-Mel-Filtermatrix
2. **Magnitude statt Power**: `np.abs(rfft)` (|X|) statt Power-Spektrum |X|² (SpeechBrain `spectral_magnitude` default power=1)
3. **Mean+Std-Norm statt Mean-only**: Zeilen 151-153 dividieren durch Std; SpeechBrain: `std_norm: False`
→ Das ONNX-Modell erhält Features außerhalb seiner Trainingsverteilung → Embedding-Ausgabe kollabiert in einen engen Kegel (Beweis B4). **Das ist die eigentliche Ursache, warum "audio" alles auf das eine Profil mappt.**
Zusatzproblem: Kein Konvertierungs-/Validierungsskript im Repo — Modell + Filtermatrix nicht reproduzierbar.

##### RC2: Keine Exklusivität bei der Speaker→Name-Zuordnung
`_identify_speakers` (transcription_tasks.py:577-891) löst jedes Gladia-Label **unabhängig** auf. Nichts verhindert Speaker 0 UND Speaker 1 → dieselbe Person. Da nur EIN Profil mit Embedding existiert (B3), gewinnt es als "best match" immer (match_speaker_from_list gibt den besten = einzigen Kandidaten zurück). Schritt 1.6 (Zeile 313-326) ersetzt dann beide Labels durch denselben Namen → Kollaps im gespeicherten Transkript.

##### RC3: Confidence-Formel ergibt 1.0 bei einem einzigen Signal
Zeile 767: `confidence = raw_score / total_signal_weight` → bei genau 1 Signal immer **1.0**, unabhängig von der Signalqualität. Beweis B2: "Speaker 1 → Abdelkader, confidence=1.00, method=audio" — ein einziges degeneriertes Audio-Signal erzeugt maximale Konfidenz und triggert Auto-Enrollment.

##### RC4: Selbstverstärkende Profil-Verschmutzung (Feedback-Schleife)
`enroll_or_update` → `update_profile_embedding` mittelt das (falsch zugeordnete) Audio von bada abada per Running Average in Abdelkaders Profil (**sample_count=17**, B3). Das Profil wird zur "Mischstimme" → matcht künftig BEIDE Sprecher noch besser → Fehler verstärkt sich mit jedem Meeting.

##### RC5: JSON `null` vs SQL NULL — zweiter Sprecher bekommt NIE ein Audio-Profil
`create_text_only_profile(embedding=None)` persistiert JSON `null` (SQLAlchemy JSON default `none_as_null=False`), Beweis B3.
- `get_profile_by_name` filtert mit SQL `Speaker.embedding.isnot(None)` → JSON `null` MATCHT
- → `enroll_or_update` findet das Text-Profil und ruft `update_profile_embedding` auf → `np.array(None, dtype=float32)` → Exception → gesamter `process_single_speaker`-Catch greift → `method=error`, Mapping verworfen
- → bada abada / Taoufik können strukturell nie ein Audio-Embedding bekommen; die Asymmetrie (1 Profil mit, 2 ohne Embedding) bleibt für immer bestehen

##### RC6: Distanz-Schwellen falsch kalibriert (für ECHTE ECAPA-Embeddings)
`speaker_profile_service.py:15-17`: HIGH=0.10 / MED=0.25 / LOW=0.40. Bei korrektem Preprocessing liegt Same-Speaker-Distanz typisch 0.3–0.6 → nach dem RC1-Fix würde mit diesen Schwellen fast alles als "no_match" verworfen. Schwellen sind aktuell nur "passend", WEIL die Embeddings degeneriert sind.

##### RC7: Original-Gladia-Labels werden nicht persistiert
`_save_transcription` speichert nur die Display-Kopie (Namen bereits ersetzt). Die rohen `Speaker 0/1`-Segmente gehen verloren → Diagnose und Reparatur alter Meetings unmöglich.

##### Sekundärbefunde
- ONNX-Reassignment (Schritt 1.5b, Zeile 230-310): kann Segmente nur ZU enrolled Profilen (= nur Abdelkader) verschieben; `reverse_map = {v:k}` kollabiert, wenn 2 Labels denselben Namen haben
- Heuristiken doppelt zum Creator gebiast: "Hauptsprecher → Creator" (Zeile 479-506) UND "Speaker 0 → erster Teilnehmer" (Zeile 569-572)

**Symptom**: `LiveKit Connection Error — could not establish signal connection: Abort handler called`

**Root Cause Analyse (livekit-docs MCP)**:
- LiveKit Dokumentation: "LiveKit does not support deployment to serverless and/or **private clusters**. Private clusters have additional layers of NAT that make it unsuitable for WebRTC traffic."
- Kind = private Cluster mit Docker-NAT → nicht kompatibel mit LiveKit WebRTC
- LiveKit pods brauchen `hostNetworking: true` + direkten UDP-Zugang
- Port-Anforderungen: 7880/TCP (Signaling), 7881/TCP (ICE TCP), 50000-60000/UDP (ICE UDP), 3478/UDP (TURN)

**Warum andere Pods (Redis, MinIO, PostgreSQL) funktionieren:**
- Diese Dienste nutzen **nur TCP** → Kind leitet TCP-Ports weiter
- LiveKit braucht **UDP** für WebRTC-Medienstrom → Kind blockiert
- WebRTC ist fundamental anders als reguläre HTTP/TCP-Dienste

**Lösung: Option A — LiveKit auf Host (Docker Compose)**
- ✅ LiveKit Server + Redis direkt auf Host gestartet (network_mode: host)
- ✅ Host hat direkten UDP-Zugang → WebRTC funktioniert
- ✅ Backend in Kind verbindet sich mit `ws://172.18.0.1:7880` (Docker Bridge Gateway)

## ⚠️ CELERY OOM — Analyse + Empfehlungen (Phase 76, 2026-06-25)

> Recording `Test 13` (532 Utterances, ~54s Audio) verursachte 6x OOMKilled trotz 16Gi Memory Limit.
> **Bestehende Logik/Struktur bleibt unverändert** — nur Vermerk für zukünftige Optimierung.

### Root Cause
| Komponente | Speicher | Persistent? | Datei |
|------------|----------|-------------|-------|
| Sentinel LLM (Qwen-1.5B Q4_K_M) | **~1.5 GB** | ✅ Immer geladen (beim Import) | `sentinel_service.py:31,76` |
| ONNX ECAPA-TDNN (192-dim) | ~120 MB | ✅ Immer geladen | `speaker_embedding_service.py:63` |
| Python + Celery + SQLAlchemy | ~300 MB | ✅ | — |
| Speaker Batch (3× librosa+fbank+ONNX) | ~150 MB | ❌ Transient | `transcription_tasks.py:655` |
| Gladia Result Dict (532 utterances) | ~20 MB | ❌ Transient | `gladia_service.py:102` |

**Berechnung**: Default Concurrency = 4 Worker进程. Jeder lädt eigenes Sentinel (1.5 GB) + ONNX (120 MB) + Python (300 MB) = **4 × 1.92 GB = 7.68 GB NUR FÜR BASELINE**. Das übersteigt jedes Memory-Limit.

### Microsoft Teams Vergleich
- Teams Audio Processing: **1-2 GB pro Worker** (Cloud-basiert, kein lokales LLM)
- Teams Speaker Diarization: **ONNX/TensorRT, ~512 MB pro Session**
- **Key Difference**: Teams lädt KEIN 1.5GB LLM pro Worker — alles API-basiert (Azure OpenAI)

### Finaler Plan (geplant)
**Ziel**: 4 Workers behalten (für Production-Throughput), Memory pro Worker reduzieren.

| Fix | Datei | Effekt |
|-----|-------|--------|
| **1. Sentinel Lazy Loading** | `sentinel_service.py:76` | Erst laden wenn `summarize_chunk()` aufgerufen wird → Idle-Worker: 300 MB statt 1.5 GB |
| **2. --max-tasks-per-child=5** | K8s Deployment Command | Prozess-Recycling nach 5 Tasks → Memory Leaks werden bereinigt |
| **3. Container Memory** | K8s Deployment | **4 Gi** (Staging) / **8 Gi** (Production pro Tenant) |

### Memory-Verbrauch nach Fix
```
Idle:   4 × 300 MB = 1.2 GB (vorher: 4 × 1.92 GB = 7.68 GB)
Active: 2 × 1.92 GB + 2 × 300 MB = 4.44 GB (nicht alle 4 laden Sentinel gleichzeitig)
Peak:   ~5 GB → passt in 4 Gi Staging / 8 Gi Production
```

### Production Architektur (pro Tenant)
- Jeder Tenant hat eigene 4 Workers (Isolated Infrastructure)
- pro Tenant: 4 Gi RAM Minimum (Staging) / 8 Gi RAM (Production, ~25€/Monat Hetzner)
- Workers bleiben 4 — für Throughput nötig wenn mehrere Meetings gleichzeitig reinkommen

### Aktueller Workaround
- Recording `45cf941f` auf `failed` gesetzt (Pipeline abgebrochen)
- Bei normalen Meetings (kurze Aufzeichnung) funktioniert die Pipeline mit 2Gi + concurrency=4
- **Nur bei großen Recordings (>500 Utterances)** ist OOM verifiziert — genaue Grenze unbekannt
